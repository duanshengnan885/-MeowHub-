## 2. 最高级开发铁律 (The Iron Laws)

### 铁律一：最小改动原则 (Minimal Diff Principle)
- 核心优先级：**1. 最小 Token 消耗 → 2. 修正确 → 3. 最小改动**。
- 只修复目标问题和必要配套改动。
- 🚫 **绝对禁止**：
  - 未经授权的大范围重构、框架重写；
  - 擅自调整代码目录层级与结构；
  - 纯格式/代码风格调整；
  - 与当前任务无关的“顺带优化”；
  - 擅自引入或升级第三方非必要依赖。

### 铁律二：当前源码为唯一真相源 (Single Source of Truth)
- 当前工作区内的代码为唯一真相源。
- 历史代码仅供查阅排查，严禁擅自回退旧版本。
- 严禁直接将 `backup`、`archive` 或外部临时文件拷贝覆盖到当前源码。

### 铁律三：需求与规划先行 (Requirements & Plans First)
- **3 步以上的复杂任务或新功能**：必须先走需求结构化流程（参考 `requirement-writer`），梳理业务定义、边界、风险与验收标准，产出规格放入 `docs/requirements/`。
- 正式开发前必须编写执行计划存入 `docs/plans/<任务名>.md`，严格遵循 `Todo / Doing / Done` 状态管理，确保长链路任务中断可无缝续跑。

### 铁律四：系统化排查，直击根因 (Systematic Debugging)
- **核心原则**：`ALWAYS find root cause before attempting fixes. Symptom fixes are failure.`（必须找到根本原因再动手，治标不治本等于失败）。
- 严禁在未定位根因的情况下盲目“试错改代码”或“碰运气猜 bug”。
- 所有 Bug 修复必须遵循四段式结构归档（见第三节）。

### 铁律五：无铁证绝不言完成 (Verification Before Completion)
- **铁律**：`Evidence before assertions always.`（必须拿实测证据说话）。
- 严禁在未运行实际验证命令、未查看实际控制台/界面输出前宣称“已修复”、“功能已完成”或“应该没问题了”。
- 宣称交付前必须执行针对性的验证命令，并附带客观的测试报告（文件 + 执行命令 + 实际输出）。

### 铁律六：安全与高危操作防线 (Security Sandbox)
- 系统执行涉及文件删除、磁盘写入、PowerShell/Shell 脚本执行或网络端口调用时，必须严格受控。
- 文件删除操作优先走安全回收站（如 `send2trash`），严禁静默执行硬删除。

## 3. 五大核心技能闭环标准

项目已在工作区装载 5 项专业技能，必须在对应场景下无条件执行：

| 技能名称 | 触发时机 | 执行准则 |
| :--- | :--- | :--- |
| **`requirement-writer`** | 新功能提案、架构调整、需求模糊时 | 引导结构化追问，产出问题定义、SRD 与 PRD 文档，明确 In/Out 范围与可量化成功指标。 |
| **`frontend-design`** | 编写或重构前端 UI/CSS 时 | 杜绝 AI 模板化平庸感（严禁滥用 warm cream 底色、生硬无脑圆角卡片、无意义渐变）。遵循星喵专属 Soft-Cute 萌系治愈与现代磨砂玻璃质感，动效克制且具备状态信息反馈。 |
| **`test-driven-development`** | 实现任何功能或修复逻辑 Bug 时 | 先写测试用例，运行并确认其失败（红），编写最小可用代码使其通过（绿），再进行安全重构。 |
| **`systematic-debugging`** | 遇到报错、异常行为或测试失败时 | 1. 读全错误堆栈与上下文；<br>2. 沿调用链反向溯源数据流，锁定第一根因；<br>3. 实施根因修复与纵深防御验证；<br>4. 连续 3 次尝试失败必须暂停重新审视假设。 |
| **`verification-before-completion`** | 任务完成、提交修改或准备交付前 | 1. 明确验证命令；<br>2. 运行全新命令；<br>3. 检查完整输出与返回码；<br>4. 确认通过后方可声明完成。 |

### Bug 记录与复盘标准化格式
每次 Bug 修复后，必须归档至 `docs/bugs_and_memory/YYYY-MM-DD.md`，涉及全局性开发经验须同步更新到本文档：
```markdown
现象：清晰描述观察到的异常症状与复现路径
根因：经过代码调用链追踪确认的技术根本原因（严禁写“可能是……”）
修复：修改的目标文件以及针对根因的最小改动方案
教训：此类问题如何防范，是否需要增加测试用例或防护断言
```

## 5. Token 极致优化与文件操作规则

1. **精准定位后读取**：
   - 必须按「目标错误文件 → 上下游调用链 → 必要配置」精准读取，单次禁止连续盲读超过 20 个文件。
   - 自动避开非源码目录：`build/`, `dist/`, `.venv/`, `.git/`, `__pycache__/`, `releases/`, `docs/scratch/`。
2. **重试机制**：
   - 网络或外部 API 调用必须采用指数退避重试：`@retry(max_attempts=3, delay=1, backoff=2)`。
3. **追踪与盘点**：
   - `.token_tracker.json`：每 10 次调用写盘，保障异常时不影响主线程。
   - `.balance_snapshot.json`：每日首次启动锁定余额基线。
   - DeepSeek 缓存命中提示规范：`🎯 缓存: X/Y tokens (Z%)`。

## 6. 交互交付与输出规范

在完成用户的任何任务时，AI 的回复必须遵循以下极简要点化规范：
1. **只返回三部分内容**：
   - **改动文件**：列出修改或新增的文件列表（必须带可点击的 `file:///` 规范链接）；
   - **改动内容**：使用标准 Markdown `diff` 代码块展现核心变更，严禁全量打印大文件；
   - **验证结果**：列出执行的验证命令、客观运行输出与测试状态。
2. **严禁冗余废话**：不重复复述用户已知的背景，重点突出关键设计决策与实测证据。
